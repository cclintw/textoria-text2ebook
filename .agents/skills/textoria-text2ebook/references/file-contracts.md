# Saved files and data ownership

## Collection layout

New books use `textoria-text2ebook/collections/<slug>/`; the registry is `textoria-text2ebook/registry.json`.

```text
source/                    Preserved original body files
source/metadata/           Original metadata attachments, when supplied
content/全文.md            Sole editable full text for a new collection
content/章節目錄.md        Outline derived from full-text headings
metadata.json              Editable basic bibliographic values
materials/                 Supplied cover and front-matter files only
intermediate/archive.json  Shared structured checkpoint
config/textoria.json       Technical configuration and collection identity
state.json                 Stage results, hashes, and review decisions
site/                      Generated static reading website
export/<title>.epub         Successfully generated and validated EPUB
```

The Chinese working filenames are existing program contracts. Keep their spelling even when instructions and documentation are in English. Create asset and attachment folders only when files are actually supplied. Do not mix source, editable work, and generated outputs.

## Authoritative files

- Preserve immutable source copies under `source/`, retaining changed originals with a hash suffix rather than overwriting earlier copies. Save original/saved paths and SHA-256 in `state.json.source`. Continue from a saved copy only after verifying it.
- Use `content/全文.md` as the only editable body and chapter source. Derive the outline from it. Requested heading changes must be reflected there, not just in the outline.
- Use `metadata.json` for manual bibliographic values. Do not overwrite it from the filename or restore deliberately removed fields.
- Keep supplied material bytes and formats under `materials/`. Preserve replacement history and hashes. Do not overwrite a cover while building.
- Derive `archive.json` from confirmed text and metadata. Preserve the schema in [schema.md](schema.md); optional sentence/token arrays are not generated by default.
- Standard website, search, and EPUB tasks never create `sqlite/`. Existing databases remain untouched. Standalone CSV, SQLite, and TEI operations require separate scope confirmation.

The explicit conversion task may write `prepared/<stem>.utf8.<ext>`, and explicit extraction may write `intermediate/plain_text.md`. Ordinary book builds retain these intermediate buffers in memory instead. Stage summaries belong in `state.json`, not separate report directories.

## Confirmation state

`state.json.reviews` contains three independent records:

| Record | Bound content and state |
|---|---|
| `chapters` | Working/outline paths, input/outline/heading hashes, review token, paragraph assignments, status, and confirmation time |
| `metadata` | Value hash and token, evidence, removed fields, imported inputs, last values, status, and confirmation time |
| `materials` | Chosen files and inspections, original/saved paths and hashes, replacement history, metadata hash, token, conflicts, invalid items, skip/status decisions, and confirmation time |

Statuses are `pending`, `confirmed`, or, for materials only, `skipped`. Store actual decisions, never inferred consent. Structural or paragraph-assignment changes reopen chapter review; metadata changes reopen its review and can affect material identity checks. Recheck saved material hashes before downstream generation. Reopen only affected checkpoints.

## Website and EPUB

The website consists of actual HTML pages, CSS/JavaScript, and one `site/data/search_index.js`. The latter sets `window.TEXTORIA_SEARCH_INDEX` as a classic script before the reader search UI; do not replace it with a fetched JSON dependency. SQLite is not read by the browser. Preserve [reader routes and behavior](theme-system.md).

EPUB identity is persisted in `state.json.epub_identity.identifier`. `epub_outputs` records published file hashes. An untracked or externally changed EPUB must not be silently overwritten. Failed validation preserves existing outputs. See [epub.md](epub.md).

## Compatibility and relocation

A legacy `clean/cleaned_text.md` remains the only editable body when already in use. Never create a second body copy alongside it. If both legacy and new working files exist, stop for an explicit choice rather than using timestamps.

Do not move `textoria-digital-library/` collections unless requested. Before an authorized relocation, back up the collection, reject an occupied destination, preserve all originals and manual edits, update registry/config/state paths, and verify the moved output without reprocessing the body. Moving a collection does not authorize moving its virtual environment.
